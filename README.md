# Ревизор

MCP-сервер и агент, который проверяет сайт по чек-листу и собирает отчёт.

В проекте три самостоятельные части, и их полезно различать сразу.

| Часть | Файл | Что это |
|---|---|---|
| **MCP-сервер** | `src/server.js` | Одиннадцать инструментов сбора данных, объявленных по протоколу Model Context Protocol. Работает с любым MCP-клиентом и ни от какой модели не зависит. |
| **Агент** | `src/agent.js` | Собственный цикл: сам поднимает сервер дочерним процессом, вызывает инструменты через API модели и собирает отчёт. |
| **Телеграм-бот** | `src/bot.js` | Оболочка над агентом: принимает адрес в переписке, показывает ход проверки и отдаёт отчёт файлами. |

Сервер можно использовать без агента — тогда порядок вызовов выбирает модель
вашего клиента. Агента можно запустить без модели вообще — тогда порядок задан
заранее. Общий у всех троих только чек-лист: 113 правил в файлах данных.

**Страница проекта:** https://qa-novchenkova.github.io/seo-revizor/ — там же полный
чек-лист из 142 проверок, включая те, которые может сделать только человек.

## Требования

**Node.js 22 или новее.** Проект собран на встроенных возможностях: `fetch`,
`process.loadEnvFile`, `AbortSignal.timeout`. Сторонних библиотек четыре.

**Браузер — только для PDF.** Отчёт в PDF собирается headless-браузером через
`--print-to-pdf`, без Puppeteer. Ищутся Chrome, Chromium и Edge по обычным путям
установки. Если браузера нет, ничего не падает: отчёт приходит в Markdown и HTML,
а PDF просто не собирается.

На сервере без графической оболочки браузер надо поставить руками:

```bash
# Debian и Ubuntu: обычный пакет, без snap
curl -fsSL https://dl.google.com/linux/linux_signing_key.pub | sudo gpg --dearmor -o /usr/share/keyrings/google-chrome.gpg
echo "deb [arch=amd64 signed-by=/usr/share/keyrings/google-chrome.gpg] https://dl.google.com/linux/chrome/deb/ stable main" | sudo tee /etc/apt/sources.list.d/google-chrome.list
sudo apt update && sudo apt install -y google-chrome-stable
```

Короткий путь `sudo apt install -y chromium-browser` тоже работает, но в Ubuntu
он ставит snap-версию, а та держит в памяти свой демон. На сервере с гигабайтом
памяти это заметно, поэтому лучше обычный пакет.

## Варианты запуска

Установка общая:

```bash
git clone https://github.com/qa-novchenkova/seo-revizor.git
cd seo-revizor
npm install
```

Дальше три способа. Разница в том, чей код крутит цикл вызовов.

### Вариант 1. Как MCP-сервер в вашем ИИ-клиенте

Сервер подключается плагином к любому приложению с поддержкой Model Context
Protocol: Claude Code, Cursor, Windsurf, Cline и Roo Code в VS Code, Claude
Desktop. Все они читают конфигурацию из готового `.mcp.json` в корне проекта.

Цикл крутит клиент, инструменты ваши. **Ключ проекту не нужен** — работа идёт
на ресурсах клиента. Дальше достаточно попросить в чате:

> следуй AGENT.md и проверь сайт https://example.com/

### Вариант 2. Автономный агент

```bash
npm run audit https://example.com/
```

Цикл крутит `src/agent.js`: сам поднимает сервер, сам выбирает вызовы, сам
собирает отчёт в Markdown, HTML и PDF. Нужен ключ доступа к модели в `.env`.

### Вариант 3. Прогон без модели

```bash
npm run direct https://example.com/
```

Те же инструменты и те же правила, но порядок задан заранее в `src/direct.js`.
Ни ключа, ни обращений к модели, ни расходов. Проверяются главная и четыре
страницы из выборки.

## Инструменты

| Инструмент | Что делает |
|---|---|
| `check_url` | Код ответа, полная цепочка редиректов, ключевые заголовки, время ответа |
| `check_meta` | Title, описание, заголовки H1–H6 и их иерархия, canonical, Open Graph, Schema.org, alt у изображений |
| `check_robots` | robots.txt: группы правил, запреты, директивы Sitemap, полное закрытие сайта |
| `check_sitemap` | sitemap.xml: список адресов, карта карт, дубли, чужие домены, даты изменения |
| `check_links` | Внутренние ссылки: битые, через переадресацию, без текста, с nofollow; структура разделов, видимая в разметке |
| `check_mirrors` | Зеркала с www и без, версия по http, дубли главной, слэш на конце, параметры, честный ли код 404 |
| `check_security` | Сертификат, защитные заголовки, cookie, смешанное содержимое, доступность `.git` и `.env`, листинг папок, показ ошибок |
| `check_analytics` | Счётчики аналитики: есть ли, везде ли, не задвоены ли, не блокируют ли отрисовку |
| `check_content` | Сравнение нескольких страниц: дубли title и описаний, повторы текста, пустые страницы, остатки демо-текста |
| `check_speed` | Core Web Vitals и что тормозит — через бесплатный PageSpeed Insights |
| `list_rules` | Весь чек-лист: идентификатор, важность, формулировка, объяснение и способ исправления |

## Что закрыто из чек-листа

В справочнике 142 пункта. Ревизор проверяет 90 из них — остальные требуют либо
человеческого взгляда, либо платных сервисов, и в чек-листе честно помечены.

| Раздел | Пунктов | Проверяет ревизор | Нужен человек | Нужен внешний сервис |
|---|---:|---:|---:|---:|
| Индексация и техническая база | 20 | 17 | 2 | 1 |
| Метатеги и заголовки | 17 | 14 | 3 | — |
| Контент и дубли | 10 | 7 | 2 | 1 |
| Скорость и Core Web Vitals | 13 | 13 | — | — |
| Мобильная версия и качество вёрстки | 17 | 12 | 5 | — |
| Юзабилити и конверсионные элементы | 19 | 2 | 16 | 1 |
| Безопасность | 13 | 9 | 4 | — |
| Аналитика и отслеживание | 9 | 4 | 5 | — |
| Анализ конкурентов | 11 | 2 | 7 | 2 |
| Проверки после внедрения | 13 | 10 | 1 | 2 |
| **Всего** | **142** | **90** | **45** | **7** |

Три колонки не пересекаются и в сумме дают число пунктов раздела.

- **Проверяет ревизор** — инструменты дают ответ сами. Сюда же входят пункты,
  где проверка автоматическая, а решение всё равно за человеком: скажем, размер
  картинки измерит инструмент, а нужна ли эта картинка вообще — вопрос к людям.
- **Нужен человек** — оценка глазами: понятно ли меню, не мешает ли баннер
  читать, выглядит ли форма заказа надёжной. Такое не измеряется запросом.
- **Нужен внешний сервис** — данные, которых у сайта просто нет: позиции в
  выдаче, частотность запросов, ссылочный профиль конкурентов.

Разделы «Мобильная версия» и «Юзабилити» закрыты слабее прочих намеренно: для
первого нужен настоящий браузер с отрисовкой страницы, для второго — живой
человек. Оба ограничения описаны в разделе «Чего проект не делает».

Отдельно ловится случай, когда страница собирается скриптами: в исходном HTML
нет ни заголовков, ни текста, и поисковик видит пустой каркас.

## Скорость: нужен бесплатный ключ

Мерить скорость самостоятельно нельзя — нужен настоящий браузер с эмуляцией
медленной сети и слабого телефона. Это делает сервис PageSpeed Insights.

Ключ бесплатный: console.cloud.google.com, включить PageSpeed Insights API,
создать ключ. Без ключа проверка не падает, а честно пишет, что раздел пропущен.

## Ключи

Скопируйте `.env.example` в `.env` и подставьте свои значения:

```
PAGESPEED_KEY=ваш-ключ
ANTHROPIC_API_KEY=ваш-ключ
```

Какой ключ когда нужен:

| Ключ | Когда нужен | Что без него |
|---|---|---|
| Ключ модели: `ANTHROPIC_API_KEY` или ключ шлюза | Только для автономного агента и телеграм-бота | Работает прогон без модели: `npm run direct` |
| `PAGESPEED_KEY` от Google, бесплатный | Для замера скорости в `check_speed` | Раздел скорости помечается как непроверенный, остальное идёт как обычно |

При работе через MCP-клиент — Cursor, Cline, Claude Code — **ключ модели проекту
не нужен вовсе**: цикл крутит клиент на своих ресурсах.

Файл `.env` закрыт в `.gitignore` и в репозиторий не попадёт. В коде ключей нет
и быть не должно: попавший в репозиторий ключ считается скомпрометированным
навсегда, потому что остаётся в истории даже после удаления из файла.

У ключа PageSpeed сразу поставьте ограничения в консоли Google:
**Application restrictions** — ваш IP, **API restrictions** — только
PageSpeed Insights API. Тогда утёкший ключ ни на что не годится.

Ключи нужны только тому, кто **запускает** проверку. Клиенту, которому вы
отдаёте готовый отчёт, ключ не нужен: он получает PDF.

## Проверять только свои сайты

> **Запускайте проверку только на своих сайтах или там, где есть разрешение
> владельца.**

`check_security` запрашивает служебные файлы вроде `.git/config` и `.env`.
Технически это обычные GET-запросы к публичному серверу: ничего не подбирается,
пароли не перебираются, ничего не ломается. Но по намерению это поиск незащищённых
служебных файлов, а такое в ряде стран приравнивается к сканированию уязвимостей —
CFAA в США, §202a в Германии, статья 272 УК в России.

Обход ссылок вдобавок создаёт нагрузку: до двадцати страниц и до сотни запросов
на проверку кодов ответа. Для своего сайта это незаметно, для чужого — незваный
трафик.

Инструмент представляется в заголовке запроса как `SEO-Revizor/0.2 (site audit bot)`,
так что в логах проверяемого сайта видно, кто приходил.

тест не требует ключа и ничего не стоит.

## Правила отдельно от кода

Проверка фиксирует только факт: сработало правило `redirect-chain`, количество — три.
Формулировка, важность и объяснение берутся из `src/rules/*.json`.

Это даёт три вещи:

1. Текст замечания правится без риска сломать логику.
2. У каждого правила постоянный идентификатор — по нему можно сравнить два прогона
   и понять, что починили, а что появилось.
3. К правилу приложены «почему это плохо» и «что делать», поэтому отчёт объясняет,
   а не просто перечисляет.

Каждая находка возвращается с полями `id`, `severity`, `title`, `message`, `why`, `fix`
и сортируется по важности: критично, важно, мелочь.

Логика намеренно отделена от протокола. Если функция неправильно работает
в `test/check.js`, через MCP она правильнее не станет — отлаживать нужно там.
Благодаря этому же те же функции можно будет подключить к телеграм-боту,
не переписывая.

## Агент

Способы запуска описаны выше, здесь — как устроен сам цикл.

Порядок вызовов выбирает модель, а не код. Она начинает с robots.txt, оттуда
узнаёт адрес карты сайта, берёт из карты представительную выборку страниц
и проверяет их, а когда данных достаточно — пишет отчёт.

Каждый ход печатается, чтобы цикл был виден:

```
  шаг 1: check_robots(url=https://example.com/)
     находок 2 (важно: 1, мелочь: 1)
  шаг 2: check_sitemap(url=https://example.com/sitemap.xml)
     находок 1 (мелочь: 1)
  шаг 3: check_meta(url=https://example.com/catalog/)
     находок 4 (критично: 1, важно: 2, мелочь: 1)
```

Цикл крутит `src/agent.js`, поэтому нужен ключ доступа к модели. Модель
задаётся переменной `REVIZOR_MODEL`. В конце показывается число потраченных
токенов и примерная стоимость прогона.

### Какая модель подойдёт

Агент целиком построен на вызове инструментов, поэтому модель обязана его
поддерживать. Без этого он не работает вовсе, а не работает хуже.

Проверено на одном и том же сайте:

| Модель | Цикл | Взяла страниц | Входящих токенов | Прогон |
|---|---|---|---|---|
| Claude Sonnet 5 | отработал | 5 из 5 | 19 672 | 12,56 ₽ |
| Claude Haiku 4.5 | отработал | 2 из 5 | 70 873 | 11,83 ₽ |

Вывод не в том, что дешёвая модель ломается — она не ломается. Она вызывает
инструменты по одному и берёт нижнюю границу выборки, отчего делает больше
кругов диалога. А на каждом круге переписка отправляется заново, поэтому
токенов уходит втрое больше и прогон обходится в те же деньги.

По умолчанию стоит **Claude Sonnet 5**: он вызывает инструменты пачками и
проходит чек-лист целиком. Opus для обхода списка избыточен — там нужна
дисциплина, а не изобретательность.

Задание для агента лежит в [AGENT.md](AGENT.md) — один и тот же текст
используют оба способа, чтобы правила не разъезжались.

Цикл можно проверить **без ключа и бесплатно**: вместо модели подставляется
заглушка, идущая по записанному сценарию.

```bash
npm run loop
```

## Отчёт

После прогона в папке `reports/<домен>/` появляются четыре файла с меткой времени:

```
2026-08-27T14-30-05.json    данные прогона — нужны для следующего сравнения
2026-08-27T14-30-05.md      для задачи в трекере или переписки
2026-08-27T14-30-05.html    для показа человеку
2026-08-27T14-30-05.pdf     для отправки заказчику
```

PDF печатается встроенным режимом Chrome или Edge, без сторонних библиотек.
Если браузер лежит в необычном месте, путь задаётся в `REVIZOR_BROWSER`.

### Сравнение с прошлой проверкой

Если по этому сайту прогон уже был, в отчёт добавляется раздел «что изменилось»:
что исправлено, что появилось нового, что осталось.

Сравниваются не тексты, а находки по ключу «правило плюс адрес» — ради этого
у правил и есть постоянные идентификаторы. В сравнение идут только страницы,
проверенные в обоих прогонах: иначе пропущенная в этот раз страница
засчиталась бы как исправленная.

Это последний чек-лист из справочника, «проверки после внедрения»: половина
проблем в SEO появляется не сама по себе, а в момент выкладки правок.

Проверить сборку документов и печать можно без модели и без ключа:

```bash
npm run report
```

## Отладочные команды

Одна проверка напрямую, без агента и без модели:

```bash
npm run check meta https://example.com/
```

Доступны `url`, `meta`, `robots`, `sitemap`, `links`, `mirrors`, `security`, `analytics`, `content`, `speed`.

Разговор с сервером по протоколу, с цепочкой из четырёх вызовов:

```bash
npm run mcp https://example.com/
```

То же самое, но с объяснениями по каждой находке:

```bash
npm run mcp https://example.com/ full
```

## Страница проекта

Собирается из файлов самого проекта, руками не пишется:

```bash
npm run site
```

Инструменты берутся из списка, который сервер отдаёт клиенту; правила — из
`src/rules/`; чек-листы — из `src/checklist/checklist.json`; порядок проверки —
из `src/order.json`. Поэтому страница не может разойтись с кодом: поменяли
правило, пересобрали — страница уже другая.

Тексты для модели и тексты для читателя разведены намеренно. `meta.description`
у инструмента и раздел «Порядок работы» в `AGENT.md` читает модель, и от их
точности зависит, правильно ли она выберет инструмент. Переписывать их под
читателя сайта нельзя, поэтому у инструментов есть отдельные поля `what` и
`why`, а у порядка — отдельный файл. Имена инструментов в `src/order.json`
сверяются со списком сервера при сборке, так что опечатка уронит сборку.

Результат кладётся в `docs/index.html`. В репозитории этого файла нет и быть не
должно: страницу собирает сам GitHub при каждом коммите в `main` — по описанию
в `.github/workflows/pages.yml` — и сразу публикует. Локальная сборка нужна
только чтобы посмотреть результат до отправки.

## Проверки самого Ревизора

Три проверки не ходят в сеть и не требуют ключа: агентский цикл гоняется на
заглушке вместо модели, разбор ответа сервиса скорости — на записанном ответе,
сборка отчёта — на записанном прогоне.

```bash
npm test
```

## Если MCP-сервер не подхватился

Файл `.mcp.json` уже в репозитории: откройте папку проекта в клиенте и
перезапустите его — инструменты появятся в списке.

Если этого не произошло, замените в `.mcp.json` относительный путь на полный:

```json
{ "mcpServers": { "seo-revizor": { "command": "node", "args": ["C:/путь/к/seo-revizor/src/server.js"] } } }
```

## Для разработчиков

**Никакого `console.log` в коде сервера и проверок.** Общение с MCP-клиентом
идёт через стандартный ввод-вывод, и печать в тот же поток ломает протокол:
клиент получает вперемешку JSON-RPC и вашу отладку и отваливается. Для отладки
только `console.error` — он пишет в поток ошибок, который клиент не разбирает.

Правила и чек-лист лежат в файлах данных, а не в коде: `src/rules/*.json` и
`src/checklist/checklist.json`. Новое правило добавляется правкой JSON, пересборка
страницы подхватит его сама. Новый инструмент объявляется в `src/server.js`
функцией `tool()`; описание для модели и описание для читателя задаются отдельно
и не должны совпадать.

Перед отправкой изменений:

```bash
npm test        # проверки без сети и ключей
npm run text    # типографика русских текстов
npm run site    # пересборка страницы проекта
```

## Телеграм-бот

Присылаешь боту адрес — получаешь отчёт файлом. Бот ничего не проверяет сам:
он запускает того же агента, что и `npm run audit`, и отдаёт результат.

```bash
npm run bot
```

Обязательна одна переменная в `.env`: `TELEGRAM_BOT_TOKEN` от
[@BotFather](https://t.me/BotFather). Ключ измерения скорости берётся оттуда же,
поэтому человеку в переписке свой ключ вводить не нужно: запрос уходит с той
машины, где запущен бот.

### Два режима

| | С моделью | Без модели |
|---|---|---|
| Что нужно | ключ доступа к модели | ничего, кроме сервера |
| Кто выбирает порядок | модель, по ходу проверки | задан заранее в `src/direct.js` |
| Страниц поштучно | решает модель | 5 |
| Отчёт | связный текст от модели | список находок без пояснений |
| Находки | одинаковые: их выдают инструменты, а не модель | |
| Стоимость прогона | от 12 ₽ | ноль |
| Время прогона | минута-полторы | полминуты |

Бот выбирает режим сам при запуске и пишет об этом в журнал. Добавили ключ,
перезапустили — включился агент; в коде бота менять нечего.

### Откуда берётся модель

Два пути, оба поддерживаются одним и тем же циклом агента.

**Напрямую у Anthropic.** В `.env` кладётся `ANTHROPIC_API_KEY`, обращения идут
через официальный SDK, счёт в долларах.

**Через OpenAI-совместимый шлюз.** Годится, когда прямой доступ недоступен или
неудобен платить: счёт в рублях, ключ один на все модели.

```bash
AI_GATEWAY_KEY=...
AI_GATEWAY_URL=https://api.timeweb.ai/v1
REVIZOR_MODEL=anthropic/claude-sonnet-5
```

Шлюз говорит на языке OpenAI, а цикл агента — на языке Anthropic: у первого
`tool_calls` внутри сообщения, у второго блоки `tool_use` и отдельные
`tool_result`. Перевод собран в `src/gateway.js` и работает на границе, чтобы
сам цикл остался нетронутым: он и есть суть проекта, и переписывать его под
каждого поставщика неправильно. Ключ шлюза важнее прямого: задан — идём через
него.

Что теряется через шлюз: размышления модели и запасная модель при упоре в
предохранитель. На выбор инструментов это не влияет.

### Сколько стоит прогон

Замеры на одном сайте, цены шлюза за миллион токенов.

| Модель | Входящие / исходящие | Прогон | Замечание |
|---|---|---|---|
| Haiku 4.5 | 135 / 1080 ₽ | ≈ 12 ₽ | дешёвая, но обходит список не целиком |
| Sonnet 5 | 405 / 2025 ₽ | ≈ 12 ₽ | зовёт инструменты пачками, токенов тратит втрое меньше |
| Opus | 675 / 3375 ₽ | ≈ 90 ₽ | для обхода чек-листа избыточна |

Вывод, который стоит помнить: **дорогая модель обошлась в те же деньги**. Цена
прогона зависит не от цены токена, а от числа кругов диалога — на каждом круге
переписка отправляется заново.

Прогон без модели можно запустить и отдельно:

```bash
npm run direct https://example.com/
```

### Оформление

Список команд, короткое и полное описание бот задаёт себе сам при запуске —
они лежат в `src/bot.js` рядом с кодом, а не только в настройках BotFather.
Под приветствием три кнопки: что проверяется, свои лимиты, ссылка на чек-лист.
Аватар ставится только вручную: BotFather, `/setuserpic`.

Отдельной библиотеки для Telegram нет: всё общение с ним — это четыре обычных
HTTP-запроса, ради которых незачем тянуть зависимость.

### Ограничения

Каждая проверка стоит денег и занимает минуты, поэтому бот считает расход:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `BOT_DAILY_LIMIT` | 5 | Проверок на человека в сутки |
| `BOT_COOLDOWN_MINUTES` | 2 | Пауза между запусками одного человека |
| `BOT_QUEUE_LIMIT` | 5 | Длина очереди; проверки идут по одной |
| `BOT_ACCESS_CODE` | пусто | Коды доступа через запятую, можно с датой окончания |
| `BOT_GLOBAL_DAILY_LIMIT` | 0 | Потолок проверок в сутки на всех вместе |
| `TELEGRAM_ALLOWED_USERS` | пусто | Если задать, бот отвечает только этим людям |
| `TELEGRAM_ADMINS` | пусто | Кому показывать расход токенов и стоимость |

Три уровня доступа, от самого открытого к самому закрытому: без настроек бот
отвечает всем; с `BOT_ACCESS_CODE` — только тем, кто знает слово из письма;
с `TELEGRAM_ALLOWED_USERS` — только перечисленным. Список тех, кто ввёл код,
лежит в `data/access.json` и переживает перезапуск.

Кодов можно задать несколько, у каждого своя дата окончания:

```bash
BOT_ACCESS_CODE=битрикс24, сеоджаз:2026-09-30, показ
```

Так на каждый отклик выдаётся свой код: видно, откуда пришёл человек, а старые
коды закрываются сами. Смена кода никого не выкидывает — уже вошедшие остаются.
Если задан `TELEGRAM_ADMINS`, при каждом входе приходит уведомление с именем,
ником и номером того, кто открыл доступ, и с использованным кодом.

### Команды

`/start`, `/help`, `/limits` — подсказка, список проверок, остаток лимитов.

Отдельно есть быстрые проверки: перепроверить одно место после правки,
не гоняя весь аудит.

```
/speed example.com       скорость и Core Web Vitals
/security example.com    сертификат, заголовки, служебные файлы
/robots example.com      robots.txt и карта сайта
/meta example.com/page   мета-теги конкретной страницы
```

Они отвечают текстом за секунды, модель не задействуют и считаются по
отдельному лимиту: `BOT_QUICK_DAILY_LIMIT` (30) и `BOT_QUICK_COOLDOWN_SECONDS` (20).

Кнопки «Что проверяется», «Мои лимиты» и «Быстрые проверки» закреплены над
полем ввода и не уезжают вместе с перепиской.

### Формат отчёта

Если на машине есть Chrome или Chromium, отчёт уходит в PDF, иначе Markdown.
Своего браузера проект не носит: печатает уже установленный, ключом
`--print-to-pdf`. На сервере ставится одной командой:

```bash
sudo apt install -y chromium
```

Без браузера бот не ломается — просто присылает Markdown.

### Что будет на большом сайте

Ограничения заложены во все проверки, поэтому размер сайта на устойчивость
не влияет:

| Где | Предел |
|---|---|
| Ответ сервера | 5 МБ, дальше обрезается |
| Вложенных карт сайта | 5 |
| Ссылок проверяется со страницы | 80 внутренних и 20 внешних |
| Страниц в обходе | 20 |
| Одновременных запросов | 3, с паузой между ними |
| Ожидание ответа | 15 секунд, две попытки |

Карта сайта MDN на 38 664 адреса разбирается за две секунды. Проверяются при
этом не все страницы, а выборка: по одной каждого типа. Смысл в том, что
десять карточек товара сделаны по одному шаблону, и дефект найдётся на первой.
